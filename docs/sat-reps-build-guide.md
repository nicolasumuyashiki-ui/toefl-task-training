## 0. 最上位の不変原則（すべてに優先する4条）

これは TOEFL版で最も高くついた学びであり、**テストの種類に依存しない**。SAT版でも初日から敷く。

1. **サーバが唯一の正本（single source of truth）**
   学習者の履歴・スコア・回答内容は**サーバ（GAS の ANSWERS / PT_RESULTS 等のシート、userId 紐付け）が正本**。
   `localStorage` / `sessionStorage` は**表示用キャッシュにすぎない**（sessionStorage はタブを閉じると消える）。
   → 表示は必ずサーバから復元できること。クライアントキャッシュはいつ消えても復旧可能な設計にする。

2. **履歴は絶対に消さない・下げない**
   問題ファイルの修正・リライト・採点ロジック調整・バグ修正のいずれでも、学習者の履歴キー
   （`training_*` / `tck_*`）・sessionStorage・サーバの回答/録音/結果シートには**一切触れない**。
   スコア表示は「上げる・保持する」方向のみ。下げる変更は明示的な仕様変更（cutoff付き）としてのみ許可。

3. **書き込みは撃ちっぱなし禁止（fire-and-forget is banned）**
   すべてのサーバ書き込みは **永続 outbox に積む → 送信 → サーバの ack を検証 → 検証後に done マーク** の順。
   「読み取りが成功した」は「書き込みが成功した」を**意味しない**（遮断環境では読みは通り書きだけ落ちる）。
   try/catch でエラーを握り潰して成功扱いにしない。

4. **キャッシュは必ず破棄できる状態にする**
   静的配信（GitHub Pages 等）はブラウザが JS を数日キャッシュする。**古いJSを掴んだままだと新コードが
   一切走らない**。修正をマージしても客先で「変化なし」になる最大の原因。**再ビルドは数分で終わるので、
   半日後の不具合は再ビルド遅延では説明できない＝キャッシュが原因と断定してよい。**

## 1. エラークラス別 ─ なぜ起きたか / SAT版でどう構造的に防ぐか

各クラスは「TOEFL版で3回以上繰り返した」ものを ★最重要 とする。SAT版は該当箇所を
**設計段階で潰す**（後から個別対処を積み重ねない）。

### ★最重要① キャッシュバスティング（PR #85, #144, #147, #148 …）
- **起きたこと**: 保存修正・履歴復元をマージしても客先PCで変化なし。#144 では「9ページだけ旧タグ残存」。
- **根因**: 手動の `?v=YYYYMMDD` 運用は**必ず漏れる**。人間が全ページを毎回揃えるのは非現実的。
- **SAT版の予防設計（初日から）**:
  - 共有アセットは **コンテンツハッシュ付きファイル名**（例 `app.a1b2c3.js`）にする。内容が変われば
    URL が変わり、旧キャッシュは自動的に無効化される。**手動 `?v=` に頼らない。**
  - それが難しい場合は **ビルド/CI で全 HTML の `?v=` を機械的に一括置換**（人手で書かない）。
  - HTML 自体にはバスターを付けられないため、**HTML×JS のスキーマ変更**（キー名・データ形式）は
    「旧HTML×新JS」「新HTML×旧JS」の両組み合わせで壊れないよう**後方互換**を持たせる。
  - 顧客案内テンプレを用意（初回のみ Ctrl+Shift+R / スマホはタブを開き直す）。

### ★最重要② データ保存の信頼性（PR #83, #92, #98, #99, #133, #136 …）
- **起きたこと**: Email/Discussion の作文が一度もサーバ保存されず消失。録音取りこぼし。模試再受験の保存失敗。
- **根因**:
  - `saveAnswers` が **JSONP GET で URL に全文を載せ**、長文が GAS の URL 上限を超えて**無言で失敗**。
  - 保存が**成功確認も再送もない撃ちっぱなし**。瞬断・即遷移・タブ閉じで消失。
  - 広告ブロッカー/社内ネットが **`script.google.com` を遮断**（読みは通り、書きだけ落ちる）。
  - 再受験が**保存成否を確認する前に「使用済み」フラグ**を立てた（#133）。
- **SAT版の予防設計（初日から）**:
  - **保存ライブラリを1本に統一**し、全書き込みがそれを通る。以下を内蔵:
    1. **永続 outbox**（localStorage キュー、`clientSaveId` で冪等化）。
    2. **大ペイロードは必ず POST**（隠しiframe form か fetch。GET に長文を載せない）。
    3. **サーバ ack 検証**（`success:true` を確認するまで未完了）。**偽成功を作らない。**
    4. **遮断回避の中継**（自社ドメインの Cloudflare Worker 等を経由できる差し込み口を最初から用意）。
  - 「完了フラグ / 使用済みフラグ / done マーク」は **ack 検証後にのみ**立てる。
  - サーバ側は **(userId, sessionId) で upsert**（追記のみは禁止。#137/#138 の 4687 重複・再受験取り違えの原因）。

### ★最重要③ スコア/バンド算定（PR #95, #110, #111, #112, #120, #127, #137）
- **起きたこと**: 練習するほどバンドが下がる／リセット／総合が各セクション以下／100%超（10/9）／模試 2930・4687 の異常表示。
- **根因**:
  - 予測を**初回(first)合算**で算出→初回が増えるほど下がる（#110）。
  - **未受験セクション=0**で総合が下がる（#95）。
  - **偽の0点**（開いただけ・保存不具合の 0/10）が集計に混入（#112）。
  - 分母が可変で 100%超（#127）。
  - **整形済み DOM テキストから数値を scrape**：`"29/ 30"` を `replace(/[^0-9]/g,'')` で `2930` に連結（#137）。
  - Google Sheets が `"5.0"` を数値化して `.0` を落とす（#146）。
- **SAT版の予防設計（初日から）**:
  - **スコア方針を初日に文書で確定**（最新の回 か ベスト か）。変更するなら **cutoff 定数を採点画面と
    同期ロジックの両方に持つ**（TOEFL版 `SCORE_CUTOFF` は my-score と history-sync に二重管理＝要同期）。
    → SAT版では **cutoff・換算表・重み・0点ガードを単一モジュール**に置き、全画面がそれを import する。
  - **分母は attempt に保存**（表示時に問題数を推測しない）。0点ガード・未受験セクションの扱いを明文化。
  - **DOM の整形済みテキストから数値を読まない**。数値はデータ構造から直接取る。保存も同様。
  - 表示直前に**数値フォーマットを正規化**（`Number(x).toFixed(1)` 等）。Sheets の型変換に注意。
  - **Admin と生徒画面は同一の採点モジュールを共有**（#148。式が分岐すると必ずズレる）。

### ★最重要④ 問題データ整合性（PR #2, #74, #100, #108, #141, #143, #78-#81）
- **起きたこと**: 練習の空欄と解答の解説が非対応／挿入問題に別テストのテキストがコピペ残存／
  Discussion に別テストのコメント混入／挿入四角が3つなのに指示は「four squares」／RDL の jp/en で正解不一致。
- **根因**: **練習ファイルと解答ファイルを別々に生成/編集**。リライト時の上書きズレ・コピペ残骸・renumber。
- **SAT版の予防設計（初日から）**:
  - **1問 = 単一ソース**（JSON等）から、練習ページと解答ページを**自動生成**する。手で両方を書かない。
  - **CI/生成時チェック**: 「練習の正解キー ⟷ 解答の正解キー」を機械照合。数（問題数・選択肢数）を照合。
  - **挿入問題は正解位置の一意性テスト必須**（discourse marker・代名詞参照で一意化）。
  - jp/en の対訳は**同一設問について述べているか**を照合（片方に別問の解説が混入する事故が頻発）。
  - 数値矛盾チェック（"of N" の N、四角の数、選択肢数、タイマー秒数）を生成時に自動化。

### ★最重要⑤ 幽霊行/ゴミ行（PR #97, #112, #113, #142）
- **起きたこと**: シートに `answers=[0,0…] / total=0 / score>0` の中身ゼロ行。「解いていない履歴」表示。
- **根因**: **ローカルの集計値や done フラグから、実体のない履歴行を合成**していた（reconcile の捏造）。
- **SAT版の予防設計（初日から）**:
  - **ローカルの done フラグから履歴行を合成しない**。提出行は**必ず実ペイロード**（実際の選択・実録音）を伴う。
  - `total>0` かつ**全回答が0/空**の行はガードで弾く（保存側でも表示側でも）。
  - 「録音した」等のマーカーは**実際に録れた時だけ**立てる。
  - 監査関数（読み取り専用の phantom 検出）を最初から用意し、定期実行。

### ★最重要⑥ タイマー/仕様準拠（PR #71, #73, #76、没 #15/34/37/38/41/45/49/50/56/64）
- **起きたこと**: overlay 表示秒数と `startTimer()` の実値が乖離。仕様書・CLAUDE.md・UI・JS の**4者不一致**。
  さらに**同一修正の重複・競合PRが10本**量産された（プロセス欠陥）。
- **SAT版の予防設計（初日から）**:
  - タイマー値・語数・問題数・配点を**単一の定数/設定ファイル**に置き、UI・採点・仕様書表示の**全てが参照**。
    値を2箇所以上に書かない。
  - 監査・修正は**単一の統合PRに束ねる**（同一問題で競合PRを作らない。下記 §4 参照）。

### ★最重要⑦ 全ページ注入の共有chrome（フッター/バナー）がレイアウト破壊（PR #91, #104, #105, #106, #131）
- **起きたこと**: 免責フッターが `position:fixed` で「次へ」ボタンに重なり押せない（15名報告）／
  `flex-basis:100%` を無条件付与し、**縦flexページで本文の高さが0になり全377ページが白紙**（#131）。
- **根因**: 全ページ共通で注入する chrome が `position:fixed`・`flex-basis:100%` を**無条件**付与。
  row flex では幅、**column flex では高さ**になる差を考慮していなかった。
- **SAT版の予防設計（初日から）**:
  - 全ページ注入の共有chromeは**レイアウト中立**にする: `position:fixed` を避け normal flow の最下部に置く。
    重なりが避けられない場合は `pointer-events:none`。flex の子として振る舞う場合は**flex 方向を判定**。
  - **ロールアウト前に row flex・column flex・モバイル幅の3条件で必ず実表示検証**（1ページだけでなく代表各種）。

### ⑧ アカウント/履歴の混線（PR #116, #145）
- **起きたこと**: 共有PCで「身に覚えのない履歴」。アカウントA→Bログインで B に A の点数が残る。
  さらに**別人名義でサーバに書き込まれる**経路（模試の `toefl_user` がセッションより優先されていた）。
- **SAT版の予防設計（初日から）**:
  - 全クライアントキャッシュキーを **userId で名前空間化**（`score_<uid>_...`）。
  - ログイン中の識別は**セッション（今ログインしている人）を最優先**。永続ログイン情報がセッションを
    上書きしない。アカウント変化を検知したら**前アカウントの表示キャッシュ＋未送信outboxをクリア**して
    サーバから取り直す（**同一アカウント再読込では絶対に消さない**）。
  - サーバ書き込み前に「このキャッシュは現アカウントの所有か（`cache_uid` 一致）」を確認するガード。

### ⑨ GAS バックエンド（PR #16, #51, #52, #60、本セッションのヘッダ不一致）
- **起きたこと**: 契約済みでも `subscription:null` で再課金プロンプト／ID列が空で照合失敗／
  未権限状態を15分キャッシュしログイン遮断／シートのヘッダ名が想定と違い「列が見つかりません」。
- **SAT版の予防設計（初日から）**:
  - 外部（Stripe 等）が populate する ID 列だけをキーにしない。**email 等の副キーで必ずフォールバック照合**。
  - **negative（未権限）状態はキャッシュしない**。positive だけ短時間キャッシュ。
  - シート読み取りは**ヘッダ名を正規化して照合**（大文字小文字・空白・`_`/`-` を無視）＋見つからなければ
    固定位置フォールバック（本セッションの Kirari 修復スクリプトの `col()` パターンを踏襲）。列番号をハードコードしない。
  - サーバ保存は **(userId, sessionId) upsert**。**追記のみ（append-only）は禁止**（重複行の温床）。

### ⑩ メディア依存のUI進行（PR #126, #128, #42）
- **起きたこと**: 音声は流れるが設問が永久に出ず白紙（設問が audio の `onended` 発火時だけ描画）。
  LCR practice 2-10 は**データに audio フィールドが完全欠落**（対症を2回重ねて真因に到達）。
- **SAT版の予防設計（初日から）**:
  - **UI 進行をメディアイベントの成功に依存させない**。必ず**タイムアウトフォールバック**（音声がどうなっても
    設問は必ず出る）。SAT は音声が少ない（主に無し）が、同原則を全ての「イベント待ち」に適用。
  - 生成データの**必須フィールド検証**を CI に入れる（欠落を早期検出）。

### ⑪ UI/HTML の定番事故（PR #19/#20, #21/#40/#77, #109, #117, #73）
- `\u####` リテラルを HTML テキスト（script 外）に直書きしない（実文字を書く）。
- `data-lang-btn` 等のボタンには**対応 handler の inline JS を同ページに必須**（answers ページで言語トグルが死ぬ）。
- 共有JS（`progress.js` 等）は**依存する inline script より前に**読み込む（順序事故）。
- 全ヘッダー/pill にモバイルのメディアクエリ（アバターにフルネームで横スクロール・ボタン画面外の溢れ）。
- i18n は `<span class="jp">…</span><span class="en">…</span>` の**ペア必須**（片方だけだと言語切替で空表示）。

## 3. 検証（verify）の必須ルール ─ 本プロジェクトで最も高くついた教訓

TOEFL版で客先を最も怒らせたのは「直したはずが直っていない」の繰り返し（#137 の後に 4687 が再発）。
原因は**理想化したデータで検証したこと**。SAT版では以下を必須とする。

1. **実データ（またはそれを模した現実的なフィクスチャ）で検証する**。壊れた値・レガシー行・
   複数attempt・空回答などの**現実の異常系**を必ずフィクスチャに含める。
2. **実際にデプロイされるコードそのものを走らせて検証する**。本セッションでは Node の `vm` に
   inline script を抽出し、DOM スタブで全レンダラを実行して期待値と突合した。ブラウザが無い環境でも
   この手法で「実コード × 実データ」を回せる。
3. **Admin と生徒で数字が一致するか等の "同値性テスト"** は、両者の実コードを抽出して同一入力で突合する。
4. 変更後は**必ず再チェック**してから「完了」と言う。テストが落ちたら落ちたと報告する。
5. マージ後は **GitHub Pages のデプロイ成否**まで確認する（失敗の前例あり。失敗なら再実行）。

## 4. 開発プロセス / PR 運用ルール

TOEFL版では**朝次監査が同一問題の重複・競合PRを10本量産**した（タイマー修正）。SAT版では:

- **1つの問題 = 1つの統合PR**。監査で複数の指摘が出たら**束ねて1本**にする。競合する小PRを乱立させない。
- **開発は指定ブランチ**で行い、マージ済みブランチに積み増さない（マージ済みPRは finished）。
- **PRは実データ検証の結果を本文に明記**（何をどう検証したか。#147/#148 の本文が良い例）。
- **破壊的変更は事前確認**。特に正解データ変更・問題数増減・スコア方針変更・履歴に触れる変更。
- **共有JSを変えたら同一コミットでキャッシュ bump**（SAT版がハッシュ名なら自動、手動運用なら忘れない）。
- **モデルIDや内部識別子をコミット/PR/コードに書かない**（チャット限定）。

## 5. SAT 固有の仕様（TOEFL との違い・要決定事項）

> ⚠️ ここは**製品判断が必要**。実装着手前にオーナーと確定すること。以下は Digital SAT（2024年〜）の
> 一般的構造の下書きで、**確定情報ではない**。数値・配点は必ず公式（College Board）で裏取りする。

**Digital SAT の一般構造（要裏取り）**
- **Reading and Writing (RW)**: 2モジュール制。各モジュール ~27問・~32分。**アダプティブ**（モジュール2の
  難易度がモジュール1の出来で変わる）。short passage + 1問 形式が中心。
- **Math**: 2モジュール制。各 ~22問・~35分。**アダプティブ**。電卓は全問使用可（Desmos 内蔵）。
- **配点**: RW 200-800 + Math 200-800 = **合計 400-1600**（TOEFL の 0-120 / Band 1.0-6.0 とは別体系）。
- **Speaking / 録音なし**（TOEFL版の LR/TI・RECORDINGS 系はSATでは不要になる可能性が高い）。
- Essay は通常なし。

**TOEFL版から引き継ぐ / 捨てる の判断が必要な要素（要決定）**
- タスク別トレーニング（TOEFL の CTW/RDL/... 相当）を SAT でも作るか、模試中心にするか。
- **アダプティブ・モジュール**をどう実装するか（TOEFL版の「Harder Module」擬似実装が参考。SATは
  モジュール2難易度分岐が本質なので、モジュール1スコアで分岐する状態遷移が要る）。
- スコア方針（最新 or ベスト）、換算表（raw→scaled の SAT 用テーブル）、cutoff の有無。
- 認証・課金（Stripe）・Admin・録音基盤を**流用するか作り直すか**（流用なら GAS の商品ID/価格ID・
  シート構成を SAT 用に分離）。
- リポジトリを**新規作成か fork か**。ブランド名（"SAT Reps" 等）とドメイン。

## 6. やってはいけないこと（SAT版でも不変）

- 学習者の履歴・スコアを**消さない・初期化しない・下げない**（原則2）。
- サーバ書き込みを**撃ちっぱなしにしない**（原則3）。
- **整形済み DOM テキストから数値を scrape しない**（#137 の 2930/4687 の教訓）。
- サーバ保存を**追記のみにしない**（upsert 必須。#138）。
- 共有chrome に**無条件の `position:fixed` / `flex-basis:100%`** を付けない（#131 白紙）。
- **理想化データだけで検証して「直った」と言わない**（§3）。
- 同一問題で**競合する小PRを乱立させない**（§4）。
- 本番の外部URL（GAS/決済）を無断で変更しない。認証ロジックを軽率に変えない。

## 付録: 主要な参照実装（TOEFL版 `toefl-task-training` 内）
これらは SAT版で「同じ機能を作るときの実装リファレンス」。丸コピーせず原則に沿って再設計するが、
ハマりどころは既に解決済みなので必ず読む。
- `js/api.js` — outbox / 大ペイロード POST / 遮断回避中継（SAVE_PROXY_URL）/ savePtResult・savePtAnswers。
- `js/auth.js` — sessionStorage フックによる全タスク自動サーバ保存 / キャッシュ userId 名前空間 / purge。
- `js/history-sync.js` — サーバ→localStorage 復元 / reconcile（幽霊行を作らない条件）/ SCORE_CUTOFF。
- `js/tm-footer.js` — 全ページ注入 chrome のレイアウト事故と対処（#131 の column-guard）。
- `js/admin-answer-overlay.js` — Admin が生徒回答を復元表示する際の 0-based↔1-based・letter正規化・
  最新attempt選択・リロードガード（#147）。
- `admin/index.html` の `predictScoresForUser` — Admin と生徒の採点を一致させる実装（#148）。
- `docs/gas-*.js` — GAS 各エンドポイント（upsert・ヘッダ正規化・negative非キャッシュ）。
- `docs/gas-phantom-audit.js` — 幽霊行の読み取り専用監査ツール。
- `CLAUDE.md` — 再発防止則の集約（本ガイドと併読）。
